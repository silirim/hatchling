# Bench method

For someone checking our numbers: what a run is, what keeps the arms comparable, and what the bench does not control. How to run it: [README.md](README.md). What it has shown: [RESULTS.md](RESULTS.md).

## What the series cost

**What a series costs.** The four-arm series of 32 runs on Opus 5.5 (`tour`, 8 runs an arm) cost about $108 at list prices; one run of `tour` is about $3 to $4, one of `fix` or `short` about $0.50. A subscription pays it out of its usage limit: 32 Opus runs use up a 5-hour window. `--wait` waits out a usage limit and then **starts spending again by itself**, for as long as runs are left: start it only when that is what you want.

**What `real` costs, as measured** (Series 5 and 6 of [RESULTS.md](RESULTS.md), list prices). On Opus 5.5 a run cost $2.44 to $4.15, **$3.15 on average**: 8 runs an arm, two arms, $50.43. On Fable 5.2 at low effort $3.42 to $4.82, **$3.98 on average**: 5 runs an arm, $39.79. A pair of Opus runs takes about an hour, so 16 runs do not fit in one 5-hour window of a subscription: the Opus series hit the limit once, and the pair it stopped was billed $3.34 for nothing.

**What `gin` costs, as measured** (Series 7, Opus 5.5, list prices). A run cost $1.27 to $2.62, **$1.92 on average**: 8 runs an arm, four arms, $61.53, no void run. The 32 runs took two hours and fit in one 5-hour window of a subscription. Before the series the estimate here was about $100, from what a run of `real` had cost: a different project did not cost the same.

**The projects.** Series 1 to 6 are on VodMax, a public Go project of this mod's own author, chosen because it is public, has a test suite and rules that gate a commit on it. The task `gin` is on a project that is not the author's: [gin-gonic/gin](https://github.com/gin-gonic/gin), a well-known Go web framework under the MIT licence. One series of it has been run (Series 7 of [RESULTS.md](RESULTS.md)), after a pilot of one run an arm on Haiku whose checks were void (see the task below). A task names its project in its `task.json` (`task`, `ref`); `--task <git url or path> --ref <commit>` run a task on any other.

## Tasks

`--work` picks a folder of `tasks/`: its `prompts.txt` (the requests), `task.json` (the checks, the project and its commit, and `"trimpath": false` where `-trimpath` breaks the project's own tests), an optional `setup.patch` applied before the session and an optional test the agent never sees.

- `tour`: ten requests, read, explain, write a test, comment, one commit, then answer from memory.
- `fix`: three defects planted by `setup.patch`, each caught by the project's tests; three commits. The history is one commit, so the defects cannot be read from a diff.
- `short`: three requests, one small feature, one commit; `accept_test.go` is copied in after the session.
- `real`: six real defects of the project at the pinned commit, found and proven by a reviewer on 2026-11-13. One chat, six requests in a row, each a user's report in Italian that names neither the file nor the fix and asks for the cause, a fix, a test and a commit. After the chat, six hidden tests are copied in one at a time (`accept_*_test.go`, never seen by the agent): each fails on the pinned commit and passes with a proof fix, which is not in this repository. A run's result is how many of the six it fixed by those tests (`fixed`, with `fixed.<id>` for each), beside the usual checks: every request answered, six commits, a test added, the project's tests passing, the tests as they were still passing on the fixed code, `gofmt`. The patch of every run is kept (`<out>/<arm>-<n>.patch`).
  - The hidden test of the first defect starts itself in 25 processes: the defect shows at some starts and not at others.
  - The one of the fourth (`rangecache`) waits for an idle release of about 25 seconds. It uses only what the product uses (the constructor, `WriteRange`, `Close`) and no field of the cache, so a fix may reshape its insides; a fix that changes the constructor's signature would not compile with it and would read as not fixed.
  - Every hidden test is run a second time when it fails, as the project's own tests are.
- `gin`: the same shape as `real`, on a project that is not ours: six real defects of gin-gonic/gin at `v1.12.0` (commit `73726dc`, 28 February 2026), each fixed later by gin's authors with a regression test. Six reports in Italian, one request each; six hidden tests in the package at the repository's root, each the authors' own regression test made self-contained, and loosened where theirs fixed a wording or a private name. The authors' fixes are the proof (`--dry --fixes <folder>`): they are not in this repository. The defects, the upstream commits and what each hidden test accepts are in [tasks/gin/NOTES.md](tasks/gin/NOTES.md). Its limits, which a reader of its results must know:
  - **The model knows gin well.** It is one of the most used Go libraries, and its code is in the training data of any model: finding the place is easier than on VodMax, for every arm alike.
  - **Three of the six fixes are at the edge of the model's training data, three after it.** By the notes of who prepared the task, for a model trained up to June 2026: the report behind `upload` is from April 2026, and the fixes of `copy`, `recovery` and `upload` were proposed between 4 and 11 June and merged on 22 June; those of `html`, `methodnotallowed` and `slowheader` were proposed and merged between July and September 2026. A model may have seen the first three.
  - **The reports point at the area more than those of VodMax.** They name public concepts of the library (the copy of the context, recovery, templates, the 405 answer, starting the server), and the one for `methodnotallowed` carries the routes that reproduce it, as the public issue did.
  - **Nothing of what came after the commit is in the clone**: see "What keeps the arms comparable". A model can still recall a fix it was trained on; no clone can prevent that.
  - **`-trimpath` is off for this task** (`"trimpath": false` in its `task.json`): with it four of gin's own tests fail at the pinned commit, untouched (`TestCustomRecovery`, `TestCustomRecoveryWithWriter`, `TestRecoveryWithWriterWithCustomRecovery`, `TestPanicInHandler`: they read file paths from a stack). Go 1.27's `gofmt` lists `binding/binding_nomsgpack.go` at that commit: it is not counted against a run. One of gin's tests (`TestSaveUploadedFileWithPermission`) reads the mode of the clone's own folder: it passes on a correct fix of `upload` only in a clone made under umask 022, which the bench sets. A pilot of one run an arm on Haiku, made before these three were handled, failed `testsPass`, `formatted` and `originalTests` in both arms with six defects of six fixed: its checks say nothing.
  - `slowheader`'s hidden test takes about 12 seconds on a fixed server and 65 on one that is not (130 with the second try): inside the 300 seconds each try of a hidden test may take.
  - Not affiliated with gin or its authors, who have no part in this bench. gin is under the MIT licence (Copyright (c) 2014 Manuel Martínez-Almeida); the bench downloads it from its public repository at each start and this repository holds no file of it. The hidden tests in `tasks/gin/` are adapted from gin's own regression tests, under that licence: its text is in [tasks/gin/LICENSE-gin](tasks/gin/LICENSE-gin).

## What a run is

- The requests of the task, sent one at a time to one headless session, on a fresh clone of a public project at a fixed commit (pinned by its id, not by a tag). The agent, its tools and the tests get a minimal environment: the variables needed to find programs, the home folder and the account, and none of the rest of your shell's. The clone has no remote.
- The arms: `clean` (no plugin), `observe` (Cachito as installed), `style` (the pet with what `/pet lean on` turns on), `leanonly` (the `cachito-lean` plugin alone, as installed: the same lines, no pet), and for comparison `caveman` and `ponytail`, each alone, loaded from the folder given with `--caveman <dir>` and `--ponytail <dir>`. An arm differs from `clean` only in what `ARMS` in `run.mjs` lists. The arms `diet` and `lean` (diet and style) of the past series are gone with the diet: those series can be run again only with the copy of the mod kept in their own folder (`<out>/mod`).
- The arm `brief` is the objection "just write 'be brief'", measured: a plugin (`bench/arms/brief`) that adds one section to the system prompt, `Be brief.`, appended last and scoped to the session as `cachito-lean` appends its lines, so the two arms differ only in the text.
  It is loaded alone from a copy kept in `<out>/brief`, and a run counts under the rule of every plugin arm: the session's `init` event lists that plugin and no other, and no hooks module failed to load.
- The arm `mini` is `Be brief.` plus only what that sentence does not cover: the three lines of the style on how the agent reads, word for word (`bench/arms/mini/text.js`).
  It is the same module as `brief` with another text, kept in `<out>/mini` and counted under the same rule.
- The cost is the one the CLI reports (`total_cost_usd`), not an estimate.

## What keeps the arms comparable

- **The clone holds the pinned commit and its past, and nothing that came after.** A whole clone of a public project carries every branch and tag of today: on `gin`, `git log master` would have listed the six fixes by their titles. The bench fetches the pinned commit alone into the copy the runs are cloned from (its ancestors, the tags on them, and one branch named as the project's default one, ending at that commit), deletes the whole clone it read from, and refuses to start, or to give a run its clone, when the repository holds any commit that is not the pinned one or an ancestor of it: reachable by a ref or a reflog, or left as a loose object (`bench/clone.mjs`, tested in `bench/clone.test.mjs`). The series up to Series 6 did not have this check: what their clones held is in Limits of [RESULTS.md](RESULTS.md).
- **The checks are measured against the project as it was at the pinned commit**, in the environment a run gets (`bench/checks.mjs`, tested in `bench/checks.test.mjs`). At every start, and with `--dry`, the bench runs the project's own tests and `gofmt -l .` on a clone of the pinned commit, with the variables the agent and the checks will have. `testsPass` and `originalTests` then ask that every package and test that passed there still passes (a test that was deleted does not) and that nothing else fails, the agent's own tests among them; `formatted` asks that `gofmt` lists no file beyond those it listed there. A result keeps what a failed check found (`why`: the tests lost and broken, the files). `manifest.json` has the flags, the umask and that start (`goflags`, `umask`, `baseline`).
- **The bench refuses to start when the project's tests fail at the pinned commit** in that environment, before any run is billed: such a failure would be in every arm and say nothing of the agent's work. It names the tests. Before 2026-11-14 the checks were absolute (`go test ./...` passes, `gofmt -l .` lists nothing) and nothing checked the start: on `gin` both arms of a pilot failed three checks that the untouched project fails.
- **The agent and the checks get the same Go flags and the same umask.** `GOFLAGS` is `-trimpath -p=2`, or `-p=2` for a task with `"trimpath": false`. The bench sets umask 022 for itself and so for every clone, session and check, whatever the shell that starts it has.
- **The modules are downloaded once, before the runs**, into `<out>/gomodcache` (`go mod download` on the pinned commit), and every run and every check then has `GOPROXY=off`: a build needs no network and finds the same modules in every run. An agent that adds a dependency the project does not have cannot download it. The files of that folder are read-only: delete it with `go clean -modcache` under the same `GOMODCACHE`, or `chmod -R u+w` first.
- Nothing of the machine's own setup is loaded: `--setting-sources project --strict-mcp-config` leaves out the person's plugins, hooks and MCP servers. Each run records what the session really had loaded, and the report leaves out a run that had anything else.
- The out dir must have no `CLAUDE.md` or `AGENTS.md` in any folder above it: `run.mjs` refuses to start otherwise.
- The runs use a copy of each plugin made at the start (`<out>/mod` the pet, `<out>/lean` cachito-lean), validated before the first run; `manifest.json` has a hash of each. A run whose hooks module did not load is left out, and the report warns when the style is not in the prompt.
- A run never touches the pet of the person who starts it. `run.mjs` sets `CACHITO_BENCH` for every session (nothing else sets it): the mod then keeps its pet, preferences and chat marks in memory, and reads and writes nothing in the person's store. cachito-lean, under the same variable, leaves out a `/lean off` kept on the machine and sends its lines. Every session also has `CACHITO_PLAIN=1`: the pet is born without the one-in-a-hundred golden roll. The lever of a run is the variable of its arm and nothing else, so a bench can start with `/pet lean` on. Before 2026-11-13 this was not so: the series up to Series 4 read and wrote the store of the person who started them (see Limits in [RESULTS.md](RESULTS.md)).
- A run that did not answer every request (a usage limit, a crash) is saved as `.failed.json`, not as a result; the bench stops after that block, and the same command resumes it. With `--wait` it waits out a usage limit and resumes by itself.
- Builds use the bench's own Go cache (`<out>/gocache`), shared by every clone and warmed before the first block. It grows with every block, because each agent changes the code and what it changed is built again: about 3.3 GB for a pair of runs of `real`, by the working notes of those series. Between two blocks, when less than 8 GB of disk are free, the bench empties that cache, warms it again and goes on; it stops only when emptying it was not enough. A full disk or an exhausted memory makes every arm fail the same way and looks like a result. `-trimpath` is what lets the clones share that cache; without it (`gin`) each clone builds the project's own packages again, and the modules it depends on stay shared. Measured on `gin` on 2026-11-14, Go 1.27.3, no model: 563 MB after the warming, then 37 MB for each further clone that runs `go test ./...` and `go test -race ./...` on untouched code (600, 637, 675 MB after one, two and three clones): about 1.2 GB more over 32 runs, before what the agents' own changes add. On VodMax the same choice once filled 28 GB: there `-trimpath` stays on.
- One run of every arm starts at the same moment, block after block, so no arm gets a different hour.
- **The checks of a block start when its last session has ended, and run one at a time** (`bench/block.mjs`, tested in `bench/block.test.mjs`). Before them the bench waits until no process of an ended session is left in a clone, up to 11 minutes, and kills what is left then. A project's tests can bind fixed ports: gin's `TestRun*` and `TestPusher` take six, and in Series 7 the checks of seven runs failed on those tests while the agent of another arm was running them (see there). Until 2026-11-14 each run was checked as soon as its own session ended, with the other arms still at work; that also held the other sessions back for as long as a check lasted. This was written after Series 7 and has not yet been through a real series.
- `manifest.json` pins the model, the CLI version, the task commit and the hashes of the prompts, the mod and the runner. For every run the folder keeps the raw events, the answers and the patch the agent committed.

## What the report can show

Every pair of arms gets an exact permutation test. With 1 or 2 runs an arm nothing is shown: the test cannot give a p under 0.33. With 4 it can reach 0.029 only when every run of one arm costs less than every run of the other. With 5 runs an arm the smallest p it can give is 0.008; 8 runs do not show a difference under about 12%. `--effort` is written in `manifest.json` and shown by the report.

## What it does not control

- The model's answers vary from run to run: that is the spread the test measures against. Four tasks on one project and one on a second say little about other kinds of work.
- Where the agent commits. The checks and the patch are read from the branch the session ends on (`HEAD`) and its working tree. A run that puts each commit on a branch of its own is read as having made only the last one: it happened once in 26 runs of `real` (run 8 of `clean`, Series 5 of [RESULTS.md](RESULTS.md)) and once in 32 of `gin` (run 1 of `caveman`, Series 7). The raw events of every run are kept, so such a run can be rebuilt and checked by hand.
- **The sessions of a block share the machine, its ports included.** The agents of the four arms work at the same time, and each runs the project's tests when it chooses. On a project whose tests bind fixed ports (`gin`) one agent's test run can make another's fail for as long as it lasts, and the other agent then spends requests on a failure that is not in its code: it happened in three blocks of eight in Series 7, to all four arms. The checks are kept out of this (see above); the sessions are not.
- There is no budget lever: `/pet budget` and the automatic compaction were removed from the mod on 2026-11-13.
